# Webhook 联动记录中心(事件台账)实施计划

## 目标

为 CD2 联动链路建立事件级台账:每个逻辑事件一行记录(成功/失败/未命中),判重从内存升级为数据库持久化(解决双通道重复),支持手动重放(成功的也可重放),不引入自动重试。前端新增「联动记录」页面。

## 一、后端 — 数据模型

**1. `backend/models.py` 新增 `WebhookEvent` 模型**(参照 `RapidUploadRetry` L284 的写法,`__admin_name__ = "联动记录"`):

- `id`、`event_key`(规范化 `action + 路径`,加索引,判重用)
- `action`(create/rename)、`file_path`(有效路径,索引)、`is_dir`(bool)
- `sources`(JSON 数组:如 `["原生 Webhook", "内部监控"]`,重复合并时追加)
- `payload`(JSON,原始报文,重放用)
- `status`:`pending / processing / success / failed / unmatched(未命中任务)`
- `error_message`(失败原因,含失败阶段:目录展开/单文件处理)
- `attempts`(int,初始 1,重放 +1)、`dup_count`(重复到达被合并的次数)
- `parent_event_id`(目录事件的子文件事件回链,索引)
- `task_id`(关联任务中心记录,索引,前端跳转用)
- `first_seen_at` / `last_event_at` / `updated_at`

表由 SQLModel 建表机制自动创建,无需手写迁移。

**2. `backend/config_manager.py` DEFAULT_CONFIG 增加 `webhook_ledger` 配置节**:`enabled`(默认 true)、`dedup_window_seconds`(默认 180——双通道实际间隔仅 5~10 秒,180 秒已有约 20 倍余量,窗口过长反而会误吞同文件的真实二次变动;漏事件可由台账+手动重放兜底)、`retention_days`(默认 90)。

## 二、后端 — 台账服务

**3. 新建 `backend/webhook_ledger.py`**:
- `record_event(action, file_path, is_dir, source, payload) -> WebhookEvent | None`:落库判重。查同 `event_key` 且 `last_event_at` 在去重窗口内的记录:
  - 无 → 插入新记录(pending),返回记录
  - 有且状态 pending/processing/success/unmatched → 更新原记录(sources 追加、dup_count+1、last_event_at),返回 None(抑制)
  - 有且状态 failed → 保守抑制:同上仅更新原记录(不自动重试),返回 None
- `update_event(event_id, status=None, error=None, task_id=None)`、`mark_replayed(event_id)`(attempts+1、状态回 processing)
- 替代 `webhook.py:26-39` 的 `_recent_events`/`_is_duplicate_event`(删除旧实现)

## 三、后端 — 接入执行链路

**4. 改造 `backend/routers/webhook.py` 的 `process_cd2_notification`(L116)**:
- 循环内判重改调 `webhook_ledger.record_event`;返回 None 计入 deduped,维持现有日志
- 命中新事件后:事件级状态落台账 —— 未命中任务 → `unmatched`;目录事件 → 状态 `processing` 交给展开逻辑;入队成功 → `success`(备注"已入队");直接同步处理的按 `asyncio.gather` 结果定 success/skipped/failed(修正现在"单文件失败仍标 completed"的问题,台账状态与任务中心状态解耦)
- 新增参数 `replay_event_id=None` 与 `skip_dedup=False`:重放时复用已有台账行、跳过判重
- **任务中心瘦身**:删除 L163-165 的整段 payload 落日志(台账已有),改为一行"原始 payload 已存联动记录 #{id}"

**5. 修复 `_expand_dir_event`(L49)**:`walk_files`(L86)目前没有 try/except,风控异常直接炸到外层——补上异常捕获,失败时任务标 error 并把父目录事件台账记录标 `failed`(error_message 记录"目录展开失败(CD2 API): ...")。子文件事件经 `process_cd2_notification` 正常落台账并挂 `parent_event_id`。

**6. 内部模拟调用方不变**:`CD2Monitor._send_webhook`、`FileProcessor._simulate_cd2_webhook`、`rapid_retry._finalize_success` 继续走 `process_cd2_notification`,台账自动覆盖这些来源(source 标注不变)。

## 四、后端 — 台账 API(新路由文件)

**7. 新建 `backend/routers/webhook_ledger.py`**,前缀 `/api/webhook-events`(注意:**不能**放进现有 `/api/webhook` 前缀——该前缀在 `main.py:141` 被加入免登录白名单,管理端点必须走鉴权):
- `GET /api/webhook-events`(列表:status/source/关键词/时间范围筛选 + 分页 + 各状态计数统计)
- `GET /api/webhook-events/{id}`(详情:payload、错误信息、子事件列表)
- `POST /api/webhook-events/{id}/replay`(重放:取存的 payload 重新走 `process_cd2_notification`,带 `replay_event_id` 复用台账行)
- `DELETE /api/webhook-events/{id}` + `POST /api/webhook-events/clear`(按时间/状态批量清理;另加按 `retention_days` 的定时清理,参照 `task_history.py` 的 `cleanup_old_tasks` 模式)

## 六、验证

- 后端:启动服务,`curl` 向 `/api/webhook/cd2/file_notify` 发测试 payload(含 create/rename/目录事件各一),确认台账落库、180 秒内双通道重复到达被合并(同 key 二次 POST 后 dup_count+1 且不重复执行)
- 重放:对一条记录调 replay 端点,确认 attempts+1、payload 重跑、状态更新
- 目录展开失败路径:用一个无效 CD2 客户端/路径触发 walk_files 异常,确认父事件标 failed 且有错误信息
- 重启进程确认台账与判重均持久(重启后窗口期内同事件仍被判重)
- 前端 build 通过,页面筛选/详情/重放交互正常

## 明确不做(本次范围外)

- 自动重试(已定不做)、重放成功事件的强制覆盖重生成、MonitorManager 队列内文件级最终结果回写台账(入队即记 success,队列执行细节看任务中心,后续有需要再加回写钩子)
